# ADR-001: Вибір брокера повідомлень для подієво-керованого конвеєра (Apache Kafka)

**Status:** Approved (Затверджено) · **Date:** 2026-11-09

Пов'язані документи: [SRS](../srs.md) · [Розділ 2. Проєктування архітектури](../2_design.md)

## Context

Система GlucoBuddy відокремлює прийом подій (Ingestion) від їх обробки трьома незалежними споживачами: Projection, Gamification, Reminder (див. [C4 Level 2](../2_design.md#diagram-level2)). Вимоги SRS, що впливають на вибір:

- [SRS-FUN-06](../srs.md#srs-fun-06): публікація з ключем `patientId` (впорядкованість подій одного пацієнта для streak та часових рядів);
- [SRS-NFR-REL-02](../srs.md#srs-nfr-rel-02): at-least-once, DLQ після 5 спроб;
- [SRS-NFR-PERF-03](../srs.md#srs-nfr-perf-03): затримка «запис → read-модель» p95 ≤ 2 с; [SRS-NFR-SCAL-01](../srs.md#srs-nfr-scal-01): consumer lag менше 1000 повідомлень;
- навантаження 500 RPS ≈ 500 повідомлень/с: усі розглянуті брокери обробляють цей обсяг із великим запасом, тому пропускна здатність не є вирішальним критерієм. Дискримінантами є порядок по ключу, незалежні consumer groups і можливість повторного читання (replay) для відновлення read-моделей CQRS.

## Alternatives

1. **Apache Kafka (KRaft).** Лог подій з партиціями, offset на кожну consumer group, retention.
2. **RabbitMQ.** Черги з acknowledgement. Для трьох споживачів потрібні три черги (fanout/topic exchange). Порядок повідомлень гарантований у межах однієї черги лише з одним споживачем; масштабування зі збереженням порядку по ключу вимагає consistent-hash exchange або single active consumer на шард черг. Для replay необхідні RabbitMQ Streams; зрілість stream-клієнтів для Go та NestJS потребує перевірки у PoC.
3. **Redis Streams.** Redis уже є у стеку; є consumer groups і replay. Обмеження: довговічність залежить від політики AOF fsync; обсяг обмежений пам'яттю; власний DLQ відсутній; спільний ресурс із кешем `CompanionState` (витіснення під навантаженням впливає на [SRS-NFR-PERF-05](../srs.md#srs-nfr-perf-05)).

## Decision

Обрано **Apache Kafka (KRaft)** за такими технічними підставами:

1. Впорядкованість гарантується в межах партиції; ключ `patientId` нативно забезпечує порядок подій пацієнта без додаткових плагінів ([SRS-FUN-06](../srs.md#srs-fun-06)).
2. Кожна consumer group (projection, gamification, reminder) має власний offset і незалежне масштабування; метрика `consumergroup_lag` прямо відповідає [SRS-NFR-SCAL-01](../srs.md#srs-nfr-scal-01).
3. Retention дозволяє replay для відновлення read-моделей (CQRS). Параметри: топік `glucose.events`, 6 партицій, retention 7 діб; джерелом істини для більш давніх даних є таблиця подій у PostgreSQL.
4. Для схеми transactional outbox → at-least-once → ідемпотентні споживачі продюсер працює з `acks=all` і `enable.idempotence=true`. DLQ реалізується застосунком у топіках `*.dlq`.

## Consequences

**Позитивні:**

- Детермінований порядок подій пацієнта; незалежне читання трьома групами; можливість replay; нативна метрика lag.
- Сумісність із протоколом Kafka в інших реалізаціях знижує ризик Vendor Lock-in.

**Негативні:**

- **Інфраструктура та відмовостійкість.** Реальна відмовостійкість Kafka вимагає мінімум 3 брокерів (replication factor 3, `min.insync.replicas=2`). На локальному стенді розгортається один брокер без реплікації. Ризик частково компенсується патерном outbox: неопубліковані події зберігаються в PostgreSQL і повторно публікуються; втрата брокера призводить до деградації [SRS-NFR-PERF-03](../srs.md#srs-nfr-perf-03), а не до втрати даних за умови цілісності таблиці подій.
- **Ресурси стенду.** Брокер на JVM споживає значну частину з 8 ГБ RAM стенду разом із PostgreSQL, TimescaleDB, Redis, Keycloak та стеком спостережуваності; потрібне вимірювання в навантажувальному тесті.
- **FinOps.** Керовані сервіси Kafka тарифікуються за брокер-години та трафік; для пілотної клініки з піком 500 RPS фіксована частина вартості переважає. Розрахунок вартості під цільове розгортання не виконано (виходить за межі роботи).
- **Фіксована кількість партицій.** 6 партицій обмежують паралелізм групи до 6 споживачів; збільшення кількості змінює відображення ключа на партицію й може тимчасово порушити порядок.
- **Додаткова затримка та навантаження від outbox.** Polling кожні 100 мс додає до 100 мс до бюджету [SRS-NFR-PERF-03](../srs.md#srs-nfr-perf-03) (2 с) і навантажує PostgreSQL; потрібне очищення опублікованих записів.
- **DLQ не вбудована.** Ретраї та DLQ реалізуються в коді трьох споживачів (збільшення обсягу роботи і тестів).
- **CI/CD.** Testcontainers для Kafka збільшують час і навантаження пайплайну GitHub Actions.
- **Крива навчання.** Offset commit, rebalancing та idempotent producer вимагають глибокого знання від одного розробника.
