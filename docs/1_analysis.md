# РОЗДІЛ 1. АНАЛІЗ ПРЕДМЕТНОЇ ОБЛАСТІ ТА АНАЛОГІВ

## 1.2 Аналіз існуючих аналогів

Для порівняння обрано три системи, що вирішують суміжні задачі дистанційного моніторингу цукрового діабету: mySugr (прямий аналог із гейміфікацією), Tidepool (відкрита платформа даних із мікросервісною архітектурою) та Dexcom API (опосередкований аналог: джерело CGM-даних із публічним API). Аналіз виконано виключно на рівні системної архітектури, протоколів обміну, стеку даних та технічних обмежень. Дані, які не підтверджені публічними джерелами, позначено як «не розкрито публічно».

### 1.2.1 mySugr

**Архітектурний патерн.** Внутрішня архітектура публічно не розкрита; належність до моноліту або мікросервісів за відкритими джерелами не підтверджується. Підтверджено використання хмарної інфраструктури AWS та керованої реляційної СУБД Aurora. За матеріалами підрядника, платформа обслуговує понад 5 млн користувачів, що вказує на горизонтально масштабований хмарний бекенд.

**Протоколи обміну.** Публічна специфікація API відсутня. За матеріалами підрядника, реалізовано інтеграцію з CGM-пристроями; протокол обміну між клієнтом і сервером не підтверджено.

**Стек даних.** Aurora; виконано міграцію з Aurora MySQL на Aurora PostgreSQL. Реляційна модель забезпечує ACID-транзакції на рівні СУБД; механізми консистентності між сервісами не розкрито публічно.

**Технічні обмеження (Technical Bottlenecks).**

1. Закрита архітектура без публічного API унеможливлює верифікацію Latency та характеристик масштабування і обмежує інтеграцію.
2. За заявою підрядника, оптимізація інфраструктури скоротила витрати на 50 %, що вказує на надлишкові інфраструктурні витрати до оптимізації.
3. Міграція між СУБД (MySQL → PostgreSQL) свідчить про вартість зміни сховища даних у довгостроковій перспективі.

**Рівень достовірності:** низький (єдине джерело — матеріали підрядника, не офіційна документація).

### 1.2.2 Tidepool

**Архітектурний патерн.** Розподілена система мікросервісів на Node.js та Go (за різними публікаціями — від близько десяти до ~18 сервісів). Сервіси розгортаються як Docker-контейнери в керованому Kubernetes (AWS EKS); маршрутизація запитів виконується через Gloo та Envoy; розгортання реалізовано за підходом GitOps. Вихідний код відкритий.

**Протоколи обміну.** HTTP-API з маршрутизацією через Gloo/Envoy; асинхронний обмін подіями через Apache Kafka (сервіс clinic-worker споживає події з Kafka-топіка для узгодження стану між сервісами). Увесь внутрішній та зовнішній трафік шифрується (TLS).

**Стек даних.** MongoDB Atlas (документна СУБД), Amazon S3 (файлове сховище). У технічній документації зазначено MongoDB 3.6.22 та образ node:10.14.2-alpine. Консистентність між сервісами забезпечується асинхронно (eventual consistency) через Kafka-споживачів.

**Технічні обмеження (Technical Bottlenecks).**

1. Версії Node.js 10 та MongoDB 3.6, зафіксовані в документації, досягли кінця підтримки (EOL) у 2021 році; документація може бути неактуальною, проте зафіксований стек є джерелом технічного боргу.
2. MongoDB 3.6 не підтримує багатодокументні транзакції (з'явились у версії 4.0), що ускладнює атомарність операцій над декількома колекціями.
3. Eventual consistency через асинхронних воркерів ускладнює відстеження стану та діагностику розбіжностей між сервісами.
4. Операційна складність експлуатації десятків мікросервісів у Kubernetes (оркестрація, шлюз, GitOps-конвеєр).
5. Міграція з EC2-інфраструктури на Kubernetes зафіксована розробниками як відповідь на витрати на супровід власних інструментів розгортання.

**Рівень достовірності:** високий (офіційна документація, технічні публікації розробників, відкритий код).

### 1.2.3 Dexcom API

**Архітектурний патерн.** Хмарна платформа збору CGM-даних із партнерським публічним API: дані завантажуються з мобільних застосунків у хмару Dexcom та надаються сторонім застосункам за моделлю pull. Внутрішня архітектура публічно не розкрита. Передбачено регіональні домени (api.dexcom.com, api.dexcom.eu, api.dexcom.jp) та середовище Sandbox.

**Протоколи обміну.** REST (HTTP, JSON); ендпоінти v3 (alerts, calibrations, dataRange, devices, egvs, events) реалізовані методом GET; вибірка виконується за часовим вікном startDate/endDate. Авторизація — OAuth 2.0 (Authorization Code, scope offline_access, Bearer-токен); транспорт — TLS 1.2 (за документацією v2). Ендпоінт dataRange з параметром lastSyncTime використовується для виявлення нових даних.

**Стек даних.** СУБД публічно не розкрито. Дані надаються як часові ряди Estimated Glucose Values (за сторонім гайдом — з інтервалом 5 хв).

**Технічні обмеження (Technical Bottlenecks).**

1. Затримка доступності даних: 1 год у США та 3 год поза США (офіційна документація v3), що виключає використання як джерела сповіщень у режимі, близькому до реального часу.
2. Pull-модель без механізму push-доставки: клієнт зобов'язаний періодично опитувати API (polling).
3. Доступ лише на читання: перелічені ендпоінти не передбачають запису подій із боку стороннього застосунку.
4. Дані CGM належать до PHI, що накладає на інтегратора вимоги мінімізації та захисту даних.

**Рівень достовірності:** високий для протоколів та затримки (офіційна документація); низький для внутрішньої архітектури (не розкрито).

### 1.2.5 Аналітичний висновок підрозділу 1.2

За результатами аналізу встановлено, що проаналізовані системи мають архітектурні обмеження, які безпосередньо впливають на надійність і своєчасність доставки медичних даних. Для mySugr внутрішня архітектура та протоколи обміну не розкриті, що унеможливлює їх інженерну верифікацію. Tidepool реалізує мікросервісну архітектуру в Kubernetes з асинхронним обміном подіями через Kafka, однак у відкритій технічній документації зафіксовано Node.js 10.14.2 та MongoDB 3.6.22, які досягли кінця підтримки, при цьому MongoDB 3.6 не підтримує багатодокументні транзакції. Dexcom API реалізує pull-модель доступу через REST із затримкою доступності даних 1 год у США та 3 год поза США, що виключає його використання як джерела сповіщень у режимі, близькому до реального часу. Серед систем із відкритою документацією (Tidepool, Dexcom API) не виявлено розділення моделей запису та читання для різних груп користувачів.

Обраний стек та архітектурні патерни спрямовані на усунення виявлених обмежень. Виділення сервісу прийому подій на Go (Fiber) забезпечує високу пропускну здатність на вході системи, а Apache Kafka розв'язує виробників і споживачів подій, забезпечує реплікацію та повторне відтворення подій, що підвищує Fault Tolerance порівняно із синхронними міжсервісними викликами. Патерн CQRS дозволяє формувати незалежні read-моделі — ігрову проєкцію стану віртуального компаньйона (Redis) та аналітичні агрегати (TimescaleDB) — без навантаження на контур запису; патерн BFF ізолює клієнтські контури дитини та батька/лікаря. TimescaleDB оптимізує зберігання часових рядів показників глюкози порівняно із загальною реляційною таблицею, а PostgreSQL забезпечує ACID-транзакції для транзакційних даних. Безпеку даних передбачено забезпечувати засобами RBAC/ABAC, OAuth2/OIDC, шифрування AES-256 та аудит-логу.

Архітектурним компромісом обраного підходу є eventual consistency між контуром запису та read-моделями, а також зростання операційної складності (Kafka, декілька СУБД, спостережуваність). Для його компенсації передбачено наскрізну спостережуваність (OpenTelemetry, Prometheus, Grafana). З проаналізованих рішень запозичено подієвий обмін через Kafka та контейнерну оркестрацію (Tidepool), а також OAuth 2.0 як механізм інтеграції із зовнішніми джерелами CGM-даних (Dexcom API); уникнуто застарілих версій компонентів, pull-моделі з багатогодинною затримкою та єдиної моделі даних для запису й аналітики. Кількісне підтвердження переваг (Latency, RPS) передбачено в Розділі 3; обґрунтування архітектурних рішень викладено в Розділі 2.
